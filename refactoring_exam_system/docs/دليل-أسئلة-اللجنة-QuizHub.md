# 2) التخزين المحلي (Local Storage) — مبدأه وإجابات اللجنة

## ما هو المبدأ؟
التخزين المحلي يعني حفظ بيانات على جهاز المستخدم داخل المتصفح، حتى لو أُغلق التبويب أو انقطع النت مؤقتاً. نحن نستخدمه لـ:
1. إبقاء الجلسة (توكنات وعضويات)
2. تفضيلات المستخدم (لغة، وصولية، ثيم)
3. حماية إجابات الطالب أثناء الاختبار (مسودة محلية)

**مو بديل عن قاعدة البيانات.** المصدر الرسمي للبيانات الحساسة والنهائية هو الـ Backend.

## ماذا نخزّن؟ (مفاتيح مهمة)

| المفتاح | المحتوى | الغرض |
|---------|---------|--------|
| `quizhub-auth` | access/refresh token + user + memberships | إبقاء تسجيل الدخول |
| `quizhub-language` | اللغة ar/en | استمرار اللغة |
| `quizhub-a11y` | تباين عالي + مقياس الخط | وصولية WCAG-oriented |
| `quizhub-theme-by-user` / `quizhub-theme-active` | الثيم | الوضع الفاتح/الداكن |
| `exam-attempt-draft:{testId}:{attemptId}` | إجابات + تعليم للمراجعة + رقم السؤال | مسودة محاولة الطالب |
| `exam-attempt-offline:{testId}:{attemptId}` | لقطة حالة انقطاع | سياسة Offline Grace |
| `exam-entry-rules:{testId}` (**sessionStorage**) | قواعد الدخول للمحاولة | جسر من صفحة الدخول |

## إجابة شفهية قصيرة
> «نستخدم localStorage مع Zustand Persist للجلسة والتفضيلات، ومسودة منفصلة لإجابات الاختبار. عند العودة نحمّل من السيرفر ثم ندمج المسودة المحلية فوقها حتى لا تضيع إجابات الطالب.»

## أسئلة متوقعة وردودها

**س: ليش localStorage مو sessionStorage للتوكن؟**  
ج: لأننا نريد بقاء الجلسة بعد إغلاق التبويب ضمن سياسة المنتج. قواعد الدخول فقط نضعها في sessionStorage لأنها مرتبطة بجلسة العمل الحالية.

**س: أليس تخزين التوكن في localStorage خطر XSS؟**  
ج: نعم هذا trade-off معروف. خففناه بـ: تحديث التوكن، اعتراض Axios، مسح الجلسة عند فشل الريفرش، وعدم تنفيذ HTML غير موثوق. بديل شائع هو HttpOnly Cookie من الباك؛ يمكن ذكره كتحسين مستقبلي.

**س: ليش ما خزّنتوا كل شيء محلياً؟**  
ج: لأن الإجابات النهائية والصلاحيات والنتائج يجب أن تبقى على السيرفر كـ Source of Truth. المحلي للاحتياط وتجربة المستخدم فقط.

# 3) Auto-Save لإجابات الطلاب — شرح كامل

## المبدأ (طبقتان)

### أ) حفظ محلي فوري
- كل ما يغيّر الطالب إجابة/تعليم مراجعة/سؤال حالي → تُحفظ مسودة في:
  - `exam-attempt-draft:{testId}:{attemptId}`
- الهدف: حتى لو انقطع النت أو انهار التبويب، ما تضيع البيانات فوراً.

### ب) حفظ دوري على السيرفر
- كل **30 ثانية** (`AUTOSAVE_INTERVAL_MS = 30000`)
- الطلب: `PUT /tests/{testId}/attempts/{attemptId}/answers`
- الجسم: `{ answers: [...] }`
- إذا الجهاز Offline → ما نرسل (نتجنّب فشل عبثي)، ونعتمد المسودة المحلية.

## الدمج عند فتح المحاولة
1. نجيب إجابات السيرفر.
2. نقرأ المسودة المحلية إن وُجدت.
3. ندمج: **المحلية تفوز عند التعارض** (`{ ...server, ...local }`).
4. إذا في مسودة محلية نعتبر الحالة «dirty» لنُرسلها لاحقاً.

## أين الكود؟
- الهوك: `src/hooks/student/useExamAttempt.js`
- المسودة: `src/lib/attemptLocalDraft.js`
- الخدمة: `saveAttemptAnswers` في `tests.service.js`

## إجابة شفهية جاهزة
> «عملنا Auto-Save بطبقتين: مسودة محلية فورية في localStorage، ومزامنة مع الباك كل 30 ثانية عبر PUT للإجابات. عند الاستئناف ندمج المحلي فوق السيرفر حتى نحافظ على آخر ما أدخله الطالب، ومع انقطاع النت نطبق سياسة Offline grace حسب نوع الاختبار.»

## أسئلة متوقعة

**س: ليش 30 ثانية مو أقل؟**  
ج: توازن بين حماية البيانات وتقليل الحمل على السيرفر/الشبكة أثناء الاختبار الجماعي.

**س: هل الحفظ عند كل حرف؟**  
ج: المحلي يتحدث مع تغيّر الحالة؛ السيرفر دوري + عند التسليم/مسارات حرجة، لتقليل الطلبات.

**س: شو بصير إذا خلص الوقت والطالب offline؟**  
ج: حسب السياسة: قد تتجمد الإجابات (`time_expired_offline`) ثم يُفرض التسليم عند عودة الاتصال.

**س: شو Offline grace؟**  
ج: مهلة **5 دقائق** (`OFFLINE_GRACE_SECONDS = 300`) تُفعَّل خصوصاً عندما يكون الاختبار مجدولاً أو فيه مراقبة. بعد المهلة تتجمد الإجابات ثم يُ强制 التسليم عند الاتصال.

# 4) إدارة الحالة — ليش Zustand مو Redux؟

## الجواب المختصر
> «اخترنا Zustand لأنه أخف وأبسط من Redux لمشروعنا، بدون boilerplate كثير، ويدعم Persist بسهولة للجلسة والتفضيلات.»

## المخازن
| المخزن | Persist؟ | الدور |
|--------|----------|-------|
| `authStore` | نعم | توكنات + عضويات |
| `languageStore` | نعم | اللغة |
| `accessibilityStore` | نعم | تباين + حجم خط |
| `themeStore` | عبر helpers | الثيم |
| `registrationStore` | لا | خطوات التسجيل |
| `passwordResetStore` | لا | نسيان كلمة المرور |
| `toastStore` | لا | إشعارات مؤقتة |

باقي شاشات العمل غالباً `useState` داخل الهوكس (محاولة الاختبار، القوائم…).

# 5) المصادقة والصلاحيات (Auth & Workspace)

## التدفق
1. Login → استلام access + refresh + memberships.
2. الحفظ في `quizhub-auth`.
3. كل طلب Axios يضيف:
   - `Authorization: Bearer <access_token>`
   - `X-Workspace-Id: <workspace الحالي>`
4. قبل انتهاء التوكن (~60 ثانية) يتم Refresh عبر `POST /auth/refresh`.
5. إذا فشل الريفرش → مسح الجلسة والذهاب لتسجيل الدخول.
6. عند 401 يُعاد المحاولة مرة بعد الريفرش.

## لماذا X-Workspace-Id؟
لأن المستخدم قد يملك عدة عضويات (مؤسسة/معلم/طالب). الهيدر يحدد سياق العمل الحالي للباك.

## إجابات جاهزة
**س: JWT ولا Session؟**  
ج: على الفرونت نتعامل مع JWT (access/refresh). الباك يصدرها؛ الفرونت يخزّنها ويحدّثها.

**س: كيف تمنعون طالب يدخل داشبورد معلم؟**  
ج: عبر Guards حسب الدور/المسار (`DashboardGuard` / `StudentDashboardGuard`) + سياق العضوية المختارة.

# 6) المعمارية (Architecture)

## التقسيم
```
pages/        → الشاشات المرتبطة بالمسارات
hooks/        → منطق الأعمال (attempt, wizard, monitoring…)
services/     → استدعاءات API فقط
lib/          → دوال وسياسات نقية (merge, offline, blueprint…)
store/        → Zustand
components/   → وحدات UI قابلة لإعادة الاستخدام
i18n/         → ملفات الترجمة
```

## مبدأ مهم
> Page يستدعي Hook → Hook يستدعي Service → Service يستخدم Axios → Lib يطبّق قواعد التحويل/السياسات.

**س: ليش هذا التقسيم؟**  
ج: فصل المسؤوليات، تسهيل الصيانة والاختبار، وتجنب تضخم الصفحات.

# 7) المراقبة (Proctoring) — تقني

## المكوّنات
- `ProctoringService` منسّق عام
- كاميرا + كشف وجه (MediaPipe BlazeFace)
- صوت محيط
- مراقبة المتصفح (تبويب، blur، نسخ، ملء الشاشة، خمول…)
- `WebSocketManager` للإرسال الحي
- REST fallback إذا فشل الـ WS: `POST .../proctoring/events`

## أحداث أمثلة
`tab_switch`, `face_lost`, `no_face`, `multiple_faces`, `copy_paste`, `fullscreen_exit`, `audio_anomaly`…

## إجابة شفهية
> «المراقبة تشتغل على جهاز الطالب: نلتقط إشارات سلوكية ووجهية، نرسلها لحظياً عبر WebSocket للمعلم/السيرفر، وإذا انقطع WS نرسل عبر REST. المخالفات تظهر كتحذير، وقد تُنهي المحاولة حسب سياسة الباك، ثم تُراجع في تقارير النزاهة.»

## أسئلة حساسة متوقعة
**س: هل المراقبة تضمن منع الغش 100%؟**  
ج: لا. هي طبقة ردع وكشف مساعدة، ترفع الثقة وتوفر أدلة للمراجعة البشرية، وليست ضماناً مطلقاً.

**س: الخصوصية؟**  
ج: تُفعَّل حسب إعدادات الاختبار، مع موافقة/فحص بيئة قبل البدء، والهدف أكاديمي ضمن صلاحيات المؤسسة.

**س: ليش MediaPipe؟**  
ج: يعمل على المتصفح بكفاءة نسبياً لكشف الوجه دون إرسال فيديو مستمر ثقيل بالضرورة لكل إطار معالجة محلية أولاً.

# 8) خوارزميات / سياسات مهمة (Algorithms & Policies)

> ملاحظة للجنة: كثير من «العشوائية النهائية» و«التصحيح» تنفَّذ على الباك. الفرونت يجهّز القواعد ويطبّق سياسات الجلسة.

## أ) المخطط العشوائي (Random Blueprint)
- المعلم يحدد بنوك + عدد أسئلة + نسب مواضيع + توزيع صعوبة (سهل/متوسط/صعب).
- الفرونت يتحقق أن النسب = 100%.
- يرسل Payload للباك: `POST /tests/{id}/questions/random-from-banks`.
- **السحب العشوائي الفعلي للأسئلة على السيرفر** (حتى تكون عادلة ومتحكم بها مركزياً).

## ب) سياسات المحاولة
- حد المحاولات (`max_attempts`) يُحترم من بيانات الدخول/الباك.
- تنقل متسلسل: منع الرجوع إذا الإعداد يفرض ذلك.
- منع التسليم مع إجابات ناقصة إذا `require_answer_all`.
- مؤقت تنازلي؛ عند الصفر تسليم إجباري (مع مراعاة حالة الاتصال).

## ج) دمج المسودة
خوارزمية بسيطة وواضحة: Spread merge حيث المحلي يطغى على السيرفر لنفس المفتاح.

## د) ريفرش التوكن
جدولة قبل الانتهاء + طابور single-flight حتى لا تنطلق عدة طلبات refresh معاً.

# 9) i18n و RTL و WCAG

## اللغة
- `i18next` + ملفات JSON Namespaces.
- العربية افتراضياً، مع تبديل `dir=rtl/ltr`.
- ترجمة رسائل الباك عبر `backendMessages`.

## الوصول (مبادئ WCAG)
- زيادة التباين: `html[data-a11y-contrast=high]`
- مقياس الخط 100%→200% عبر `--a11y-font-scale` و`zoom` على جذور محددة.
- يظهر في إعدادات الطالب ويؤثر على مسار الاختبار.

**صيغة دقيقة للجنة:**  
> «ندعم مبادئ الوصول وفق توجّه WCAG عبر تباين عالٍ وضبط حجم الخط، دون الادعاء بشهادة اعتماد رسمية كاملة لكل المعيار.»

# 10) أسئلة بزنس / منتج

**س: ما المشكلة التي تحلونها؟**  
ج: تشتت أدوات التقييم (إنشاء/نشر/مراقبة/تصحيح/تحليل) وضعف التكامل ودعم العربية والوصولية في بعض الحلول.

**س: من المنافس؟**  
ج: منصات اختبار عامة/عالمية وأدوات مجزأة (Forms + جداول + مراقبة منفصلة). تميزنا بالدورة المتكاملة + العربية/RTL + مساحات عمل مؤسسية + مراقبة مربوطة بالتصحيح والتحليل.

**س: من الفئة المستهدفة؟**  
ج: مؤسسات، معلمون (مؤسسة أو مستقل)، وطلاب.

**س: ما القيمة؟**  
ج: تقليل التكلفة التشغيلية للتقييم، رفع موثوقية الجلسة، وتسريع التصحيح واتخاذ القرار عبر التحليلات.

**س: كيف تربح المنصة مستقبلاً؟** (إن سألوا)  
ج: اشتراكات مؤسسات، باقات مراقبة/تحليلات متقدمة، أو ترخيص سنوي — حسب نموذج التخرج/التوسع.

**س: ما المخاطر؟**  
ج: اعتماد الشبكة أثناء الذروة، محاولات التحايل على المراقبة، وحساسية بيانات الطلاب → تُعالَج بسياسات حفظ/مراقبة وصلاحيات وتحسينات أمنية مستمرة.

# 11) أسئلة «غراء النظام» (Integration / Glue)

**س: كيف يرتبط الفرونت بالباك؟**  
ج: REST عبر Axios + WebSocket للمراقبة الحية. كل الطلبات تحمل التوكن ومعرّف المساحة.

**س: ماذا لو الباك رجع خطأ؟**  
ج: نوحّد رسالة الخطأ، نترجمها إن أمكن، ونعرض Toast/رسالة واضحة للمستخدم.

**س: Deep link لاختبار طالب؟**  
ج: رابط دخول؛ إن لم يكن مسجلاً نوجّهه ثم نعيده للرابط بعد تسجيل الدخول/اختيار المسار.

**س: كيف تنتقل بيانات المراقبة من صفحة الدخول للمحاولة؟**  
ج: عبر جسر جلسة (entry session bridge) حتى لا نعيد فحص البيئة من الصفر بلا داعٍ.

# 12) أسئلة UI/UX وتصميم

**س: ليش معالج متعدد الخطوات للاختبار؟**

ج: لأن الحساب قد يملك عدة مسارات؛ المستخدم يحتاج رؤية/إضافة/إدارة واضحة.

**س: دعم الموبايل؟**  
ج: الواجهات Responsive، مع ملاحظة أن المراقبة بالكاميرا أفضل على أجهزة مناسبة؛ يمكن ذكرها كقيد واقعي.
